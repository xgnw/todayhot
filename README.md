# 全网今日热榜（纯 HTML 版）

由原 **PHP + SQLite** 版本改造而来。核心变化：**不再需要服务器和数据库**，双击 HTML 文件即可运行，并在此之上加入了两种自动更新能力。

---

## 一、为什么原版必须用 PHP？改造的关键在哪

原版每个平台都要用 `curl` 抓取，是因为这些官方接口**绝大多数不返回跨域响应头**（`Access-Control-Allow-Origin`）。

浏览器有一条铁律：**同源策略**。你从 `file://` 或自己的域名发起 `fetch` 到 `weibo.com`，服务器没授权跨域，浏览器会把拿到的响应直接丢弃 —— 请求发出去了，数据却读不到。这就是必须有个"在服务器上跑"的抓取程序的原因。

所以"改成纯 HTML"不等于"删掉抓取逻辑"，而是**把抓取这件事从浏览器里挪出来**，同时想办法让浏览器也能拿到数据：

| 层次 | 手段 | 覆盖范围 | 需要什么 |
|------|------|----------|----------|
| ① 快照 | `update.py` 抓取后写入 `hot-data.js`，页面直接读 | 全部 46 个平台 | 本机装 Python |
| ② 直连 | 浏览器直接请求自带跨域头的接口 | 微博 / 头条 / 抖音 / GitHub | 无 |
| ③ 代理 | 经 CORS 代理转发请求 | 全部 46 个平台 | 部署一次 Worker |

三层是**自动降级**关系：页面优先用最新数据，某一层拿不到就退回上一层，任何一层失效都不会白屏。

> 关于 `hot-data.js` 为什么不是 `.json`：`file://` 协议下 `fetch('hot-data.json')` 同样会被同源策略拦截，而 `<script src="hot-data.js">` 不受限制。一行数据写成 `window.__HOT_DATA__ = {...}` 就能被直接读取 —— 这是让"双击打开"成为可能的关键细节。

## 二、文件说明

| 文件 | 作用 |
|------|------|
| `index.html` | 主页面。单文件包含全部样式与逻辑，**双击即可运行** |
| `hot-data.js` | 数据快照，由 `update.py` 自动生成，不用手改 |
| `update.py` | 抓取脚本，零第三方依赖（只用标准库），把 PHP 的抓取逻辑移植而来 |
| `sync_order.py` | 把 `index.html` 的 `DEFAULT_ORDER` 同步给 `update.py` 与 `hot-data.js`，保证三处顺序一致 |
| `verify_order.py` | 模拟"新电脑 / 版本未变 / 版本 +1"等场景，验证默认排序真的生效 |
| `自动更新.bat` | Windows 双击运行的入口，可选"更新一次"或"常驻自动更新" |
| `proxy-worker.js` | Cloudflare Worker 跨域代理，部署后浏览器可实时拉取全部平台 |
| `hot-data.json` | 可选导出（加 `--json` 参数时生成），方便别的程序复用数据 |

## 三、快速开始

**第一步：看页面**
双击 `index.html`。此时显示的是快照数据，无需任何环境。

**第二步：更新数据（三选一）**

**方式 A · 手动跑一次**
双击 `自动更新.bat`，选 `1`。

**方式 B · 常驻自动更新（推荐）**
双击 `自动更新.bat`，选 `2`。窗口保持开启，每 30 分钟自动抓取一次并覆盖 `hot-data.js`，刷新浏览器就是最新数据。

改间隔：编辑 `自动更新.bat` 里的 `set INTERVAL=30`。
没装 Python：把文件里的 `set PY=python` 改成 python.exe 的完整路径。

**方式 C · 系统计划任务（开机自动，无窗口）**
以管理员身份运行一次下面的命令，之后每 30 分钟自动更新一次：

```
schtasks /create /tn "全网热榜更新" /tr "python.exe \"C:\完整路径\热榜\update.py\"" /sc minute /mo 30 /f
```

命令行直接使用：

```bash
python update.py                 # 抓一次
python update.py --loop 30       # 常驻，每 30 分钟
python update.py --only weibo,baidu,zhihu   # 只更新指定平台
python update.py --workers 8     # 提高并发（默认 6，别调太大以免被限流）
python update.py --json          # 额外导出 hot-data.json
```

## 四、开启浏览器内实时更新（可选，但推荐）

不做这一步，浏览器里只有 4 个平台能实时刷新（微博 / 头条 / 抖音 / GitHub）。做了之后，46 个平台全都能在页面内自动拉取，**完全不用跑脚本**。

**部署代理（约 2 分钟）**

1. 登录 Cloudflare → Workers 和 Pages → 创建 Worker
2. 把 `proxy-worker.js` 的全部内容粘贴进去，部署
3. 复制你的 Worker 地址，形如 `https://xxxx.workers.dev`
4. 打开页面 → **设置** → 在「CORS 代理前缀」填入：

```
https://xxxx.workers.dev/?url=
```

5. 点「测试代理」验证，出现"代理可用"即成功

填好后页面会按设定间隔自动拉取全部平台，顶部状态栏的绿点会显示更新状态。

> 安全提示：Worker 里默认开启了域名白名单（只允许热榜相关域名），**不要**随便把 `ALLOW_ANY` 改成 `true`，否则你的 Worker 会变成任何人都能用的开放代理，可能被人刷流量。

**不想自建？** 也可填公共代理，例如 `https://api.allorigins.win/raw?url=`，但公共代理速度慢、有速率限制，稳定性和隐私都不如自建。

## 五、页面功能

- **自动更新**：顶栏开关控制，间隔可选 5 / 10 / 30 / 60 分钟；页面切到后台时暂停，回到前台且数据过期会自动补一次
- **搜索**：顶栏输入关键词，跨全部板块过滤，无匹配的板块自动隐藏
- **设置**：深色模式、板块排序（每行「⏫置顶 / ↑上移 / ↓下移 / ⏬置底」按钮，或拖拽手柄；上方名称筛选框快速定位）、板块显隐、每板块显示条数、代理地址、恢复默认排序 / 导出当前排序
- **详情**：点板块右上角「更多 ›」查看该平台完整榜单
- **数据状态**：状态栏圆点颜色表示数据新鲜度（绿=新鲜 / 黄=偏旧 / 红=很旧），并显示"实时 N 个"表示有多少平台是本次实际拉取的
- **本地缓存**：页面成功拉到的数据会存进浏览器 localStorage，下次打开立即显示（快照只作为兜底）

### 改默认板块排序（让任何电脑打开都一致）

排序原本有**三层来源**，这是"换台电脑顺序就变"的根因：

| 层 | 位置 | 谁决定 |
|---|---|---|
| ① 页面默认 | `index.html` 的 `DEFAULT_ORDER` | **基准，唯一需要改的地方** |
| ② 快照顺序 | `hot-data.js` / `update.py` 的 `sort` 字段 | 由 `sync_order.py` 从 ① 同步过去 |
| ③ 本机覆盖 | localStorage `rebang_settings_v1.order` | 谁在谁机器上拖过，那台机器就永久记住 |

**改法**（两步，缺一不可）：

1. 编辑 `index.html` 里的 `DEFAULT_ORDER`，按想要的先后调整 pkey
2. **把紧跟其后的 `ORDER_VERSION` 加 1**

第二步是关键：`ORDER_VERSION` 是"推送开关"。别人电脑里已经存了旧顺序，只有看到版本号变了，才会重新拉取你的新默认顺序；否则它们会继续用自己的那份。（自己机器上想预览效果，也可以直接点「恢复默认排序」。）

不想手抄 pkey？**设置弹窗 → 用每行的「⏫置顶 / ↑上移 / ↓下移 / ⏬置底」按钮调顺序（也可拖拽 ⠿ 手柄），上方筛选框按名称快速定位要挪的板块 → 点「复制当前排序」**，会生成可直接粘贴的数组，粘过去再把版本号 +1 即可。

改完跑一条命令让三处重新对齐（**不联网**，就地重排快照 + 更新 `update.py`）：

```
python sync_order.py           # 先看会改什么
python sync_order.py --apply   # 真正写回
```

> 不在 `DEFAULT_ORDER` 里的平台会自动接到末尾，不会因为漏写而消失。
> `verify_order.py` 模拟「新电脑 / 手动调过顺序但版本没变 / 手动调过且版本 +1 / 点恢复默认 / 点复制排序」五种情况，
> 用无头浏览器渲染后读实际 DOM 顺序比对，改完跑一遍就知道有没有真的生效。

### 关于自适应布局

列数和宽度都由 CSS 变量驱动，**改一处、全局跟随**：

```css
--cols  由断点决定（当前列数）
--shell = cols × card-max + (cols-1) × gap + 2 × gutter   ← 内容区宽度，是 cols 的函数
```

关键是 **内容区宽度不是写死的常量，而是列数的算式**。`.container` 和 `.topbar-inner` 共用 `--shell`，所以顶栏和内容区的左右边缘永远对齐，不存在"两处各写一个 1560px 慢慢失配"的问题。

| 视口宽度 | 列数 | 单卡宽度 |
|---|---|---|
| < 620px（手机） | 1 | 铺满 |
| 620 ~ 1059 | 2 | 约 300–430px |
| 1060 ~ 1419 | 3 | 约 330–400px |
| 1420 ~ 1779 | 4 | 约 340–400px |
| 1780 ~ 2119 | 5 | 约 355–400px |
| 2120 ~ 2459 | 6 | 约 350–400px |
| ≥ 2460（4K） | 7 | 约 350–400px |

两个设计取向：

- **列数由断点显式给，不用 `auto-fill` 被动挤出来**。`auto-fill` 在断点前那一刻会把卡片拉到 450px 以上才换行，跨过去又骤降到 300px，宽度抖动很明显。
- **单卡封顶 400px（手机除外）**，超宽屏不是无限拉伸，而是整体居中留白 —— 3440px 下内容区 2948px，两侧各留 234px，卡片仍是 400px。想要铺满只需调 `--card-max`。

调整方式：改断点就调媒体查询里的 `--cols`，改松紧就调 `--card-max`，两者都不用碰 JS。

> `layout_probe.py` 是配套的验证脚本：抽出页面的 `<style>` 套一个最小 DOM，用无头浏览器逐个分辨率实测**列数 / 卡宽 / 顶栏是否错开 / 有没有横向溢出**。改完布局跑一遍，比目测可靠。

### 关于板块图标

默认使用**从各站 favicon 下载、矢量化后内联进页面的真实图标**，**46 个板块全部是内联 SVG**（`data:image/svg+xml`），**0 个 base64 PNG、0 个外链请求、0 个色块兜底**。

其中 `v2ex`、`nodeseek` 是**手写** SVG（几何体，最清晰），其余 44 个由 `svgify.py` 把源站位图**自动矢量化**而来。

#### 为什么不直接 `<img src="https://各站/favicon.ico">`

实测 46 个源站图标，问题比想象中多：

| 现象 | 真因 |
|---|---|
| 爱范儿 **584 KB**、原神 232 KB | 源 `.ico` 打包了多分辨率，一个 16px 图标拖半兆流量 |
| 36氪返回 `text/html` | 错误页，`<img>` 解析不了 |
| **sspai.com/favicon.ico 是 404**（571 字节 HTML 错误页） | 图标其实在 CDN：`cdn-static.sspai.com/favicon/sspai.ico` |
| **www.ceic.ac.cn/favicon.ico 只有 58 字节且残缺** | 换 `www.cenc.ac.cn/earthquake-manage-publish-web/favicon.ico` 才有真图标 |
| **v2ex / nodeseek 官方地址被本机代理 502 挡死** | 改从图标镜像 `a.favicon.im/<domain>` 取，再做几何量测 → 手写 SVG |
| github / 36kr 主站地址失效 | 需换 CDN（已写进脚本 `FALLBACK`） |
| 防盗链、网络波动 | 本地打开时 Referer 为空会被拒 |

> **教训**：写 favicon 地址时「能返回 200」不等于「图标有效」——404 的 HTML 页面、58 字节的残缺 `.ico`、1×1 红点占位图，统统返回 200。`fetch_icons.py` 已用「Pillow 能否解码 + 边长 ≥ 8px」双重过滤这类假图标。

所以图标是**预先下载 + 归一化 + 矢量化 + 内联**的，不是在页面里现讨。效果：**零外部请求、必定显示、离线可用、任意缩放不糊**，页面也不再为图标等待网络。

#### 体积账（实测 46 个）

| 阶段 | 总体积 |
|---|---|
| 源站原始 `.ico` | 约 1 MB |
| 归一化 32×32 + 调色板量化 PNG | 约 50 KB |
| 旧方案：base64 PNG 内联 | 约 65 KB |
| **现方案：内联 SVG（文本）** | **约 126 KB** |
| **上层 gzip 之后的实际传输量** | **约 34 KB（旧方案 42 KB）** |

> **关键取舍**：换成 SVG 后，**原始文件变大**（126 KB vs 65 KB，单文件 `index.html` 现 178.5 KB），
> 但 **gzip 后反而更小**（34 KB vs 42 KB）——SVG 是重复度极高的文本，压缩率碾压 base64。
> 部署到会开 gzip/brotli 的静态托管时整体更省；若必须计较硬盘上的裸文件大小，
> 把 `fetch_icons.py` 里的 `USE_SVG` 改回 `False` 即可回到 base64 PNG。

#### 矢量化是怎么做的（svgify.py）

每个图标按「颜色层」拆开，对每层：**marching squares 取亚像素等值线 → 闭合环 → Ramer-Douglas-Peucker 抽稀 → 输出 `<path>`**。

两个决定成败的细节：

1. **颜色层必须互不重叠**。早期版本给每个颜色算一个「颜色接近度」标量场各自求轮廓，各层覆盖面互相叠压，画在上层的会把下层的镂空糊掉——sspai 的 π、新浪的大眼睛、ifanr 的 N 就是这么丢的。改成**硬分区**（每像素只归最近色，相邻色块共享边界）后所有分区正好铺满，不再靠叠放顺序赌。这就是 `vectorize` (v1，软边) 与 `vectorize2` (v2，硬分区) 的差别。
2. **`viewBox` 必须是完整画布 `0 0 64 64`，不能按内容包围盒裁紧**。裁紧会让「内容不满幅」的图标（内容只占 52/64）在塞进同一个方框时被整体放大 20%+，跟原图错位。这曾让 ifanr 和 sspai 的评分崩到 0.04 / 0.25，看着像形状描错了，其实是坐标系被偷偷缩放。

每个图标生成 v1/v2/v2e/v2c 四套候选，用 `pick_best.py` 渲染后按客观指标择优，胜者的参数记进 `fetch_icons.py` 的 `VECTOR_MODE` 表。

#### 质量是怎么验收的（不靠肉眼）

```
sim = 1 - diff(原图, SVG) / diff(原图, 纯白)
```

`diff` 在**同等高斯模糊**之后算（原图是 LANCZOS 软边、SVG 是硬边，硬碰硬会把整条轮廓都判失配）。
另做**错位对照**：拿隔壁图标的 SVG 去比同一张原图，确保高分不是蒙出来的。

`verify_final.py` 是最终关卡——它直接读 `index.html` 里成品的 data URI，按页面完全相同的方式（`esc()` 后拼进 `<img src>`）渲染并逐格比对。

**当前实测：46 个图标全部渲染有内容，可比对 44 个平均 sim 0.794、最低 0.599**（v2ex/nodeseek 无 PNG 参照不参与评分）。

> 为什么立指标而不靠肉眼：同一张缩略图给不同人看能得出相反结论，而一会儿说"这块没事"、
> 一会儿说"这块错了"最耽误事。上面的量尺校准过程本身就是证据——几次误判都来自量尺歪了
> （偏移错位、背景基准不一致、宽页面卡渲染），而不是算子本身错了。

#### v2ex / nodeseek 为什么是手写 SVG

这两个平台的 logo 全是**规整几何体**，矢量描述比位图更清晰（任意缩放不糊、HDPI 友好）且体积小一个数量级：

| 平台 | 几何构成（32 网格实测值） | SVG 体积 vs 位图 |
|---|---|---|
| V2EX | 五边形外框（左竖边 x=7）+ 中间梭形槽，`fill-rule="evenodd"` 挖空 | 266 B vs ~1.6 KB |
| NodeSeek | 三道 ±60° 灰弧 r=14.7/11.6/8.6 + 黑脸圆 r=6.7 + 两条 1×3 白竖眼 | 903 B vs ~3 KB |

**所有数值都是对 `a.favicon.im` 原图做 32×32 像素测量得来的，不是目测估计的。**
实测方式：把图降采样到 32 网格，按亮度/alpha 分类打印字符图，再做半径与包围盒统计。

> **踩过的坑**：自动轮廓提取（行扫描 + Douglas-Peucker）在这两个图标上**失败了**——
> v2ex 中间那个梭形槽是内部孔洞，只记外边界会把它整个丢掉（path 只剩 4 个点）；
> nodeseek 是 6 道离散弧 + 1 个黑脸的多连通图形，被切成 78 个碎块，全部被点数下限过滤掉。
> 教训：**轮廓自动提取适合单一连通块，遇到孔洞/多连通就老实手工描。**

#### 手写 SVG 存在哪 / 怎么改

源文件：`svg源/v2ex.svg`、`svg源/nodeseek.svg`（备份在同目录 `_归档_多余文件/热榜SVG源/`，含原始参考 PNG）。

它们的 data URI 写死在 `fetch_icons.py` 的 `HANDMADE_SVG` 里，**不是**直接改 `index.html`——
因为 `ICON_MAP` 整块每次重跑都会被替换，直接改页面会在下次跑脚本时静默丢失。
三条路径都要过 `with_handmade()` 合并回来：

```bash
python fetch_icons.py            # 联网重抓
python fetch_icons.py --no-fetch # 离线用缓存
```

改完 SVG 只需把新 data URI 粘进 `HANDMADE_SVG` 再跑一次即可，无需改任何页面代码
（`iconUrl()` 对 `ICON_MAP` 的值不做类型判断，直接返回，PNG 和 SVG 混着用没问题）。

#### 重新生成（源站换图标时可重跑）

```bash
pip install pillow                 # 仅需一次
python fetch_icons.py              # 联网重抓 + 压缩 + 注入
python fetch_icons.py --no-fetch   # 用本地缓存重新压缩注入（离线可用）
```

脚本会打印每个平台「原始字节 → 内联后」并说明剔除原因。注入前自动备份为 `index.html.bak`，注入后自检三件事：

1. ICON_MAP 块必须落进某个 `<script>`（追加到 `</html>` 之后会被浏览器当纯文本丢弃，页面照常显示但 JS 一行不跑）
2. `</script>` / `</html>` 必须在（防止注入把文件截断成静默半残）
3. **注入后图标总数不能少于注入前**——抓取大面积失败时宁可拒绝写入，也不能把已有 42 张图清成 0

#### 当前状态

- **44 个**源站 favicon 经 `svgify.py` 自动矢量化后内联
- **2 个**手写 SVG 内联：`v2ex`、`nodeseek`（几何体，最清晰）
- 内联数据合计 **125.8 KB**：SVG **46 个** / base64 PNG **0 个**
- 实测：46 板块 / 46 图标 / 内联 `<img>` 46 个 / **外部请求 0** / 色块兜底 0 / `index.html` **178.5 KB**

相关脚本：

| 文件 | 作用 |
|---|---|
| `svgify.py` | 位图 → SVG 的矢量化模块（`vectorize` / `vectorize2`） |
| `pick_best.py` | 多套候选渲染打分择优，产出 `_svgout/chosen.json` |
| `verify_final.py` | 端到端验收：读成品 `index.html` 渲染并逐格比对 |
| `fetch_icons.py` | 抓取 + 矢量化 + 注入（含退步保护） |

想退回 PNG：把 `fetch_icons.py` 里的 `USE_SVG` 改成 `False` 重跑即可，页面代码一行都不用动。

#### 设置项

`设置 → 板块图标` 四选（默认第一项）：

1. **内置源站图标** —— 推荐，离线可用（46 个内联 SVG，共约 126 KB，零外部请求）
2. **品牌色圆角块** —— 纯色块，不含文字
3. **网站原始图标** —— 实时联网拉取，失败自动回退色块
4. **不显示图标**

> 兜底徽标是纯色圆角块（`rect` + `rx=7.5`）、不含任何文字，作为色标使用；平台名称由板块标题（`<h2>`）承担。想给兜底色块换个颜色，改 `index.html` 里的 `BRAND` 表：`pkey: ['品牌色']`。

## 六、与原版 PHP 的功能对照

| 功能 | 原 PHP 版 | 本版本 |
|------|-----------|--------|
| 数据库 | SQLite（`data/rebang.db`） | 不需要，数据在 `hot-data.js` |
| 服务端 | 必须（PHP + curl） | 不需要，或用 Cloudflare Worker 替代 |
| 定时抓取 | 宝塔计划任务 + `cron.php` | `update.py --loop` 或系统计划任务 |
| 后台管理 | `admin/`（登录、平台增删、手动更新） | 改为页面内设置面板（板块排序 / 显隐） |
| 平台配置 | 数据库表 | `update.py` 顶部的 `PLATFORMS` 列表 |
| SEO 设置 | 数据库 settings 表 | 直接改 `index.html` 的 `<title>` / `<meta>` |
| 历史快照 | `hot_history` 表 | 未保留（如需可加，见下） |
| 平台数量 | 48 个（部分已失效） | 46 个（全部实测可用） |
| 新增平台 | 改数据库 | 在 `update.py` 的 `PLATFORMS` 加一行即可，页面无需改动 |

**关于新增平台**：页面有一条通用规则 —— 凡是没有专属抓取器的平台，一律走 `uapis.cn` 通用接口，`type` 就等于 `pkey`。所以只要在 `update.py` 的 `PLATFORMS` 数组加一行 `('平台标识', '名称', '图标URL', 序号, ('uapis', '平台标识'))`，页面会自动出现对应板块，**不用同步改前端**。

## 七、常见问题

**Q：图标显示不出来 / 有的有有的没有？**
现在 46 个图标全部预先内联进页面（44 个自动矢量化 SVG + 2 个手写 SVG），正常情况不会再有这个问题。即使某个源站日后改版取不到图，页面也会自动回退成品牌色圆角块，不会空白。想 100% 稳定就保持默认的「内置源站图标」。

**Q：双击 `index.html` 后板块显示"暂无数据"？**
说明 `hot-data.js` 没有生成或为空。运行一次 `update.py` 即可。

**Q：页面能打开，但状态栏一直显示"未配置代理"？**
这是正常的 —— 未部署代理时只有 4 个平台能实时更新，其余使用快照数据。按第四节配置代理即可全部实时。

**Q：`update.py` 报某个平台"无数据"？**
第三方接口偶尔会限流或改版。脚本会跳过失败的平台，**不会**清空已有数据；下次更新成功会自动补上。若某平台连续多天失败，通常是接口变了，可换成 `('uapis', '该平台的type')` 走聚合接口。

**Q：GitHub 趋势拿不到数据？**
GitHub 未登录接口限额为每小时 60 次。若你更新很频繁（比如 5 分钟一次），可能触发限额，等一小时会自动恢复。

**Q：能不能部署到 GitHub Pages / Cloudflare Pages？**
可以，把 `index.html` 和 `hot-data.js` 一起上传即可（`update.py` 在本地跑，定时把新的 `hot-data.js` 推上去）。部署到线上时建议同时配好代理，这样访客打开页面也会自动实时更新。

**Q：想保留历史榜单（对比昨天同一时间的排名变化）？**
原版靠 `hot_history` 表实现。本版本未包含，如需可在 `update.py` 里加一个函数：每次写完 `hot-data.js` 后，把当前数据按日期另存一份到 `history/YYYY-MM-DD.js`，页面再按需对比。

## 八、发布到 GitHub / 静态托管（文件清单）

本项目是纯静态站点，**运行时只需要两个文件**，其余都是本地工具链（可选发布，方便别人复现）。

### 必须发布的（决定页面能不能跑）

| 文件 | 说明 |
|------|------|
| `index.html` | 主页面（含全部逻辑、样式、46 个内联 SVG 图标） |
| `hot-data.js` | 数据快照，`index.html` 通过 `<script src="hot-data.js">` 加载 |

> 两文件必须放在**同一目录**（页面用的是相对路径）。GitHub Pages 默认根目录，直接传上去即可。

### 建议一起发布的（工具链 + 文档，让项目可复现）

| 文件 | 作用 |
|------|------|
| `README.md` | 本说明 |
| `update.py` | 抓取脚本（标准库零依赖），生成 `hot-data.js` |
| `sync_order.py` | 把 `index.html` 的 `DEFAULT_ORDER` 同步给 `update.py` / `hot-data.js` |
| `verify_order.py` | 无头浏览器验证默认排序真的生效 |
| `fetch_icons.py` | 图标抓取 + 矢量化 + 注入（需 Pillow） |
| `svgify.py` / `pick_best.py` | 图标矢量化的底层模块，被 `fetch_icons.py` 调用 |
| `verify_final.py` | 图标端到端验收 |
| `layout_probe.py` | 布局自适应验证 |
| `proxy-worker.js` | 可选：Cloudflare Worker 跨域代理，部署后全平台实时刷新 |
| `自动更新.bat` | 可选：Windows 双击入口，常驻自动更新 |

### 不要发布的（已用 `.gitignore` 排除）

| 路径 | 原因 |
|------|------|
| `_归档_多余文件/` | 开发期临时脚本 / 验证产物归档 |
| `__pycache__/` | Python 缓存 |
| `_icons_opt/` `_icons_raw/` `_svgout/` | 图标处理中间产物 |
| `svg源/` `热榜SVG源/` | SVG 源 / 备份（已归档） |
| `预览.png` | 本地预览截图，非必要 |
| `hot-data.json` | 前端不引用，是 `update.py --json` 的可选导出（如需可取消忽略） |

### 上线后怎么更新数据

数据更新完全在本地：跑一次 `update.py` 生成新的 `hot-data.js`，把它 **commit + push** 上去，GitHub Pages 几秒到一分钟内自动生效。线上访客刷新即见最新。若配了代理（第四节），访客页面还会自己实时拉取，连推送都省了。

### 可选：自定义域名 / 404

- 自定义域名：在仓库 **Settings → Pages** 填域名并加 `CNAME` 文件（内容为你的域名）。
- 404 页：GitHub Pages 可放一个 `404.html`（可选，非必需）。
